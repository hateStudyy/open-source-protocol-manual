2.2 TCP 与 UDP 对比 TCP vs UDP

同为传输层协议，设计目标截然不同。

TCP（传输控制协议）
  • 面向连接：三次握手建立连接
  • 可靠传输：确认 + 重传 + 校验
  • 有序到达：序列号保证顺序
  • 流量控制：滑动窗口机制
  • 拥塞控制：慢启动 / 拥塞避免
  • 全双工：双向同时通信
  • 字节流：无消息边界
  • 开销较大：首部 20~60 字节
典型场景：网页浏览、文件传输、邮件、SSH、数据库连接
VS
UDP（用户数据报协议）
  • 无连接：直接发送，无需握手
  • 不可靠：不保证送达，无确认
  • 无序：不保证到达顺序
  • 无流量控制：应用自行处理
  • 无拥塞控制：可能丢包
  • 支持多播 / 广播
  • 数据报：保留消息边界
  • 开销最小：首部仅 8 字节
典型场景：视频 / 语音通话、在线游戏、DNS 查询、直播流

2.3 HTTP 版本演进 HTTP Version Evolution

从 HTTP/1.0 到 HTTP/3，核心改进一目了然。

HTTP/1.0
1996
  • 每个请求一个 TCP 连接
  • 无持久连接（非标准 Keep-Alive）
  • 无 Host 头（最初）
  • 简单的请求 / 响应模型
→
HTTP/1.1
1997
  • 持久连接（默认 Keep-Alive）
  • 管道化（Pipelining，但有队头阻塞）
  • 分块传输编码
  • Host 头必须
  • 缓存机制完善
→
HTTP/2
2015
  • 多路复用（解决队头阻塞）
  • 二进制分帧
  • 服务器推送（Server Push）
  • 头部压缩（HPACK）
  • 流优先级
→
HTTP/3
2022
  • 基于 QUIC（UDP）
  • 彻底解决 TCP 层队头阻塞
  • 0-RTT / 1-RTT 快速握手
  • 连接迁移（换 IP 不断连）
  • 内置 TLS 1.3
传输层变迁： HTTP/1.x → TCP HTTP/2 → TCP (+ TLS) HTTP/3 → QUIC (UDP + TLS 1.3)

2.5 HTTP 与 WebSocket HTTP vs WebSocket

HTTP 是请求-响应模式，WebSocket 建立后实现全双工持久通信。

HTTP 请求-响应
Client → 请求
Server → 响应
（连接关闭或等待下次请求）
Client → 请求
Server → 响应
半双工高开销（每次带完整头部）无服务器主动推送
WebSocket 全双工
HTTP 升级握手（101 Switching Protocols）
⇅ 双向实时消息帧
⇅ 服务器可主动推送
⇅ 持久连接直到关闭
全双工低开销（帧头仅 2~14 字节）服务器主动推送

2.7 RESTful API 架构风格 RESTful Architecture

REST 不是协议，而是基于 HTTP 的架构约束集合。

REST 六大约束

客户端-服务器
前后端分离，各自独立演进
无状态
每次请求包含所有信息，服务器不保留会话
可缓存
响应需标明是否可缓存，提高效率
统一接口
资源标识、自描述消息、超媒体驱动（HATEOAS）
分层系统
客户端无法判断直连服务器还是中间层
按需代码（可选）
服务器可发送可执行代码到客户端
