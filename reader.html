1. Overview
1. 概述
The Hypertext Transfer Protocol (HTTP) is a stateless application-level request/response protocol that uses extensible semantics and self-descriptive messages for flexible interaction with network-based hypertext information systems.
超文本传输协议（HTTP）是一种无状态的应用层请求/响应协议，它使用可扩展的语义和自描述的消息格式，用于与基于网络的超文本信息系统进行灵活交互。
HTTP is a generic interface protocol for information systems. It is designed to hide the details of how a service is implemented by presenting a uniform interface to clients that is independent of the types of resources provided.
HTTP 是面向信息系统的通用接口协议。它通过向客户端提供独立于所提供资源类型的统一接口，来隐藏服务的实现细节。
2. Request Methods
2. 请求方法
GET: Transfer a current representation of the target resource. GET is safe and idempotent.
GET：获取目标资源的当前表示形式。GET 是安全且幂等的。
HEAD: Same as GET, but transfer the status line and header section only. HEAD is safe and idempotent.
HEAD：与 GET 相同，但仅传输状态行和首部部分。HEAD 是安全且幂等的。
POST: Perform resource-specific processing on the request content. Not safe nor idempotent by default.
POST：对请求内容执行特定于资源的处理。默认不是安全的，也不是幂等的。
PUT: Replace all current representations of the target resource with the request content. Idempotent.
PUT：用请求内容替换目标资源的所有当前表示形式。幂等。
DELETE: Remove all current representations of the target resource. Idempotent.
DELETE：移除目标资源的所有当前表示形式。幂等。
CONNECT: Establish a tunnel to the server identified by the target resource.
CONNECT：建立一条通往目标资源所标识服务器的隧道。
OPTIONS: Describe the communication options for the target resource.
OPTIONS：描述目标资源的通信选项。
TRACE: Perform a message loop-back test along the path to the target resource.
TRACE：沿通往目标资源的路径执行消息回环测试。
PATCH: Apply partial modifications to a resource.
PATCH：对资源应用部分修改。
3. Status Code Classes
3. 状态码分类
1xx (Informational): The request was received, continuing process. 2xx (Successful): The request was successfully received, understood, and accepted. 3xx (Redirection): Further action needs to be taken in order to complete the request. 4xx (Client Error): The request contains bad syntax or cannot be fulfilled. 5xx (Server Error): The server failed to fulfill an apparently valid request.
1xx（信息性）：请求已接收，继续处理。 2xx（成功）：请求已成功接收、理解并被接受。 3xx（重定向）：需进一步操作以完成请求。 4xx（客户端错误）：请求包含错误语法或无法被满足。 5xx（服务端错误）：服务器未能完成一个看似有效的请求。
Common codes: 200 OK, 201 Created, 204 No Content, 301 Moved Permanently, 302 Found, 304 Not Modified, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 405 Method Not Allowed, 409 Conflict, 429 Too Many Requests, 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout.
常见状态码：200 成功，201 已创建，204 无内容，301 永久重定向，302 临时重定向，304 未修改，400 错误请求，401 未授权，403 禁止访问，404 未找到，405 方法不被允许，409 冲突，429 请求过多，500 服务器内部错误，502 网关错误，503 服务不可用，504 网关超时。
4. Message Format
4. 报文格式
An HTTP message consists of a start-line, followed by a (possibly empty) sequence of header fields, an empty line indicating the end of the header section, and finally an optional message body.
HTTP 消息由起始行、一系列（可能为空的）首部字段、表示首部结束的空行，以及可选的消息正文组成。
Request: <method> <request-target> <HTTP-version> Response: <HTTP-version> <status-code> <reason-phrase>
请求行：<方法> <请求目标> <HTTP 版本> 响应行：<HTTP 版本> <状态码> <原因短语>
5. Safe and Idempotent Methods
5. 安全方法与幂等方法
Request methods are considered "safe" if their defined semantics are essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server as a result of applying a safe method to a target resource.
如果请求方法的既定语义本质上是只读的，则该方法被视为"安全方法"；即客户端对目标资源应用安全方法时，既不请求也不期望源服务器发生任何状态变化。
A request method is considered "idempotent" if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request. GET, HEAD, PUT, DELETE, OPTIONS, and TRACE are idempotent.
如果使用某请求方法进行多次相同请求对服务器产生的预期效果等同于单次同样的请求，则该方法被视为"幂等方法"。GET、HEAD、PUT、DELETE、OPTIONS 和 TRACE 是幂等的。
6. HTTPS (HTTP over TLS)
6. HTTPS（基于 TLS 的 HTTP）
HTTPS is the use of HTTP over a TLS connection. When TLS is used, the agent that initiated the TLS handshake (the client) negotiates a secure channel with the server. All HTTP request and response data is transmitted through this encrypted channel.
HTTPS 即通过 TLS 连接使用 HTTP。使用 TLS 时，发起 TLS 握手的代理（客户端）与服务器协商出一个安全通道，所有 HTTP 请求和响应数据均通过此加密通道传输。
HTTPS provides three guarantees: confidentiality (data is encrypted), integrity (data cannot be altered in transit without detection), and authentication (the server's identity can be verified using certificates).
HTTPS 提供三项保障：机密性（数据被加密）、完整性（传输中的数据被篡改可被检测到），以及身份认证（可通过证书验证服务器的身份）。
The default port for HTTP is 80; the default port for HTTPS is 443.
HTTP 默认端口为 80；HTTPS 默认端口为 443。
7. Caching and Connection Management
7. 缓存与连接管理
HTTP caching is controlled by Cache-Control, ETag, Last-Modified, Expires and related headers. Proper cache usage reduces latency and server load.
HTTP 缓存由 Cache-Control、ETag、Last-Modified、Expires 等首部控制。合理使用缓存可降低延迟和服务器负载。
HTTP/1.1 supports persistent connections by default (keep-alive), allowing multiple request/response pairs to share a single TCP connection. HTTP/2 introduces multiplexing; HTTP/3 runs over QUIC.
HTTP/1.1 默认支持持久连接（keep-alive），允许多个请求/响应对共用同一个 TCP 连接。HTTP/2 引入了多路复用；HTTP/3 运行于 QUIC 之上。

TCP / UDP 协议

Transmission Control Protocol / User Datagram Protocol

基于 RFC 9293 (TCP)、RFC 768 (UDP)。位于传输层，为 IP 层之上的应用提供端到端的数据传输服务。

English (Original)

中文对照

1. TCP Overview
1. TCP 概述
The Transmission Control Protocol (TCP) is intended for use as a highly reliable host-to-host protocol between hosts in packet-switched computer communication networks. TCP provides reliable, ordered, and error-checked delivery of a stream of bytes between applications.
传输控制协议（TCP）旨在作为分组交换计算机通信网络中主机之间高可靠的主机到主机协议。TCP 为应用程序之间的字节流提供可靠、有序、经过差错检验的交付。
TCP is connection-oriented: a connection must be established before data is exchanged. TCP is designed to operate over IP and deliver data reliably to the destination.
TCP 是面向连接的：在交换数据之前必须先建立连接。TCP 设计为运行于 IP 之上，将数据可靠地送达目的端。
2. TCP Core Features
2. TCP 核心特性
Reliable delivery: TCP uses sequence numbers, acknowledgments, checksums, and retransmission of lost segments to ensure all bytes are delivered correctly and in order.
可靠交付：TCP 使用序列号、确认、校验和以及丢失段的重传机制，确保所有字节按正确顺序完整送达。
Flow control: The receiver advertises a window size so that the sender does not overwhelm the receiver's buffer.
流量控制：接收方通告窗口大小，使发送方不会压垮接收方的缓冲区。
Congestion control: TCP detects network congestion via packet loss and round-trip-time changes, and adjusts sending rate using algorithms such as slow start, congestion avoidance, fast retransmit, and fast recovery.
拥塞控制：TCP 通过丢包和往返时间变化检测网络拥塞，并使用慢启动、拥塞避免、快速重传和快速恢复等算法调整发送速率。
Full-duplex: Data can be transmitted in both directions simultaneously on the same connection.
全双工：同一连接上的数据可双向同时传输。
3. TCP Three-Way Handshake
3. TCP 三次握手
TCP uses a three-way handshake to establish a connection: Step 1: Client sends SYN (seq=x) to server. Step 2: Server replies SYN+ACK (seq=y, ack=x+1). Step 3: Client replies ACK (seq=x+1, ack=y+1). Connection is now established.
TCP 通过三次握手建立连接： 第一步：客户端发送 SYN（seq=x）给服务器。 第二步：服务器回应 SYN+ACK（seq=y, ack=x+1）。 第三步：客户端回应 ACK（seq=x+1, ack=y+1）。连接建立完成。
TCP closes a connection via a four-way handshake: each side sends a FIN and receives an ACK, independently terminating its direction of the full-duplex channel.
TCP 通过四次挥手关闭连接：每一方各自发送 FIN 并接收 ACK，独立地终止全双工通道中自己方向的连接。
4. UDP Overview
4. UDP 概述
The User Datagram Protocol (UDP) provides a procedure for application programs to send messages to other programs with a minimum of protocol mechanism. The protocol is transaction oriented, and delivery and duplicate protection are not guaranteed.
用户数据报协议（UDP）为应用程序提供了一种以最少协议机制向其他程序发送消息的方式。该协议面向事务，不保证交付和防重复。
UDP is connectionless: datagrams can be sent without any handshake. Each datagram is self-contained, consisting of a source port, destination port, length, checksum, and payload.
UDP 是无连接的：数据报可在无需握手的情况下发送。每个数据报都是自包含的，由源端口、目的端口、长度、校验和以及载荷构成。
5. UDP Core Features
5. UDP 核心特性
Low overhead: The UDP header is only 8 bytes, minimizing per-packet cost. No connection setup, flow control, or congestion control is performed by the protocol itself.
开销低：UDP 首部仅 8 字节，使每包开销最小化。协议自身不执行连接建立、流量控制或拥塞控制。
Unreliable: UDP does not guarantee delivery, ordering, or duplicate protection. Applications must handle reliability if needed.
不可靠：UDP 不保证交付、顺序或防重复。如有需要，应用程序必须自行处理可靠性。
Supports broadcast and multicast, which TCP does not.
支持广播和多播，而 TCP 不支持。
6. Typical Use Cases
6. 典型适用场景
TCP: HTTP/HTTPS, SSH, SMTP, FTP, database connections — any scenario where reliable, ordered delivery is required.
TCP 适用：HTTP/HTTPS、SSH、SMTP、FTP、数据库连接 —— 任何需要可靠且有序交付的场景。
UDP: DNS queries, VoIP, online games, real-time video/audio streaming, DHCP, SNMP — scenarios where low latency matters more than perfect reliability.
UDP 适用：DNS 查询、VoIP、网络游戏、实时音视频流、DHCP、SNMP —— 低延迟比完美可靠性更重要的场景。
7. Key Differences
7. 关键区别
Connection: TCP connection-oriented / UDP connectionless. Reliability: TCP reliable / UDP best-effort. Ordering: TCP ordered / UDP unordered. Header size: TCP 20+ bytes / UDP 8 bytes. Speed: TCP slower due to overhead / UDP faster. Transmission: TCP byte stream / UDP discrete datagrams.
连接性：TCP 面向连接 / UDP 无连接。 可靠性：TCP 可靠 / UDP 尽力而为。 顺序性：TCP 有序 / UDP 无序。 首部大小：TCP 20+ 字节 / UDP 8 字节。 速度：TCP 因开销较慢 / UDP 更快。 传输方式：TCP 字节流 / UDP 离散数据报。

DNS 域名系统协议

Domain Name System

基于 RFC 1034 (概念)、RFC 1035 (实现)。将便于人类识别的域名映射为 IP 地址的分层分布式命名系统。

English (Original)

中文对照

1. Overview
1. 概述
The Domain Name System (DNS) is a distributed, hierarchical database that associates information with domain names assigned to each of the participating entities. Most prominently, it translates human-friendly domain names (such as example.com) into the numerical IP addresses needed for locating and identifying computer services and devices with the underlying network protocols.
域名系统（DNS）是一种分布式的分层数据库，将信息与分配给各参与实体的域名关联起来。其最重要的功能是将人类易识别的域名（如 example.com）转换为底层网络协议用于定位和识别计算机服务与设备所需的数字 IP 地址。
2. Hierarchical Namespace
2. 分层命名空间
The domain name space is a tree structure. Each node has a label (up to 63 octets) and a full domain name is the sequence of labels from that node to the root, separated by dots. The root is represented by the empty label.
域名空间是树状结构。每个节点都有一个标签（最多 63 个八位字节），完整域名即为从该节点到根节点的标签序列，以点号分隔。根节点由空标签表示。
Hierarchy levels: Root (.) → Top-Level Domains (TLD: com, org, cn, io, ...) → Second-Level Domains (example.com) → Subdomains (www.example.com).
层级结构：根（.）→ 顶级域（TLD：com、org、cn、io 等）→ 二级域（example.com）→ 子域名（www.example.com）。
3. DNS Servers
3. DNS 服务器类型
Recursive Resolver: A server that receives queries from clients and issues further queries as needed to produce a final answer.
递归解析器：接收客户端查询并按需发起后续查询，最终产生答复的服务器。
Root Name Servers: Return references to TLD name servers. There are 13 logical root servers labeled A through M.
根域名服务器：返回对顶级域（TLD）服务器的引用。共有 13 个逻辑根服务器，标记为 A 至 M。
TLD Name Servers: Manage top-level domains (.com, .org, .cn) and refer queries to authoritative servers for registered domains.
顶级域名服务器：管理顶级域（.com、.org、.cn 等），并将查询转交给已注册域的权威服务器。
Authoritative Name Servers: Hold the actual DNS records for a given domain and provide authoritative answers for queries about it.
权威域名服务器：持有特定域名的实际 DNS 记录，并对该域名的查询提供权威答复。
4. Common Record Types
4. 常见记录类型
A: Maps a domain name to an IPv4 address. AAAA: Maps a domain name to an IPv6 address. CNAME: Canonical name, aliases one domain to another. MX: Mail exchange records for the domain. NS: Name server authoritative for the domain. TXT: Arbitrary text data (SPF, DKIM, verification). PTR: Reverse mapping from IP to domain. SOA: Start of authority; administrative information about a zone.
A：将域名映射到 IPv4 地址。 AAAA：将域名映射到 IPv6 地址。 CNAME：规范名，将一个域名作为另一个域名的别名。 MX：该域的邮件交换服务器记录。 NS：该域的权威域名服务器。 TXT：任意文本数据（用于 SPF、DKIM、验证等）。 PTR：从 IP 反向映射到域名。 SOA：起始授权记录；关于区域的管理信息。
5. Query Resolution Process
5. 查询解析过程
A typical resolution for www.example.com: 1) Client queries its configured recursive resolver. 2) Resolver checks its cache; if miss, queries a root server for .com referrals. 3) Resolver queries the .com TLD server, which returns the authoritative server for example.com. 4) Resolver queries the authoritative server, which returns the A record for www.example.com. 5) Resolver caches the answer (per TTL) and returns it to the client.
以 www.example.com 的典型解析为例： 1) 客户端向其配置的递归解析器发起查询。 2) 解析器查询缓存；未命中则向根服务器请求 .com 的推荐。 3) 解析器向 .com 顶级域服务器查询，得到 example.com 的权威服务器。 4) 解析器向权威服务器查询，获得 www.example.com 的 A 记录。 5) 解析器按 TTL 缓存该结果并返回给客户端。
6. Transport and Security
6. 传输与安全
DNS traditionally runs on UDP port 53, with TCP port 53 used for large responses and zone transfers. Secure variants include DNS over TLS (DoT, port 853) and DNS over HTTPS (DoH).
DNS 传统上使用 UDP 端口 53，对大响应和区域传输使用 TCP 端口 53。安全变体包括 DNS over TLS（DoT，端口 853）和 DNS over HTTPS（DoH）。
DNSSEC (DNS Security Extensions) adds cryptographic signatures to DNS records so resolvers can verify authenticity and integrity of responses.
DNSSEC（DNS 安全扩展）为 DNS 记录添加加密签名，使解析器能验证响应的真实性与完整性。
Every DNS record has a TTL (time-to-live) field, indicating how long a resolver may cache the record before re-querying.
每条 DNS 记录都有 TTL（生存时间）字段，指示解析器在重新查询前可缓存该记录的时间长度。

WebSocket 协议

The WebSocket Protocol — RFC 6455

基于 RFC 6455。提供在单个 TCP 连接上的全双工通信通道，用于浏览器与服务器之间的实时交互。

English (Original)

中文对照

1. Overview
1. 概述
The WebSocket Protocol enables two-way communication between a client running untrusted code in a controlled environment to a remote host that has opted-in to communications from that code. The protocol consists of an opening handshake followed by basic message framing, layered over TCP.
WebSocket 协议使运行在受控环境中的不受信任客户端代码与选择接受此类通信的远程主机之间能够进行双向通信。该协议包括一次打开握手，随后是基于 TCP 的基本消息帧传输。
The goal of this technology is to provide a mechanism for browser-based applications that need two-way communication with servers that does not rely on opening multiple HTTP connections.
该技术的目标是：为需要与服务器进行双向通信的浏览器端应用提供一种不依赖于打开多个 HTTP 连接的机制。
2. Core Characteristics
2. 核心特性
Full-duplex: Once the connection is established, both client and server can send messages independently at any time.
全双工：连接建立后，客户端和服务器可在任意时刻相互独立地发送消息。
Single long-lived TCP connection, reducing the overhead of repeatedly establishing new HTTP connections for real-time data.
单个长连接的 TCP 连接，避免了为实时数据反复建立新 HTTP 连接的开销。
Low overhead per message: after the handshake, messages are sent in small frames with a header of as little as 2 bytes.
每条消息开销低：握手完成后，消息以小帧形式发送，帧头最少仅 2 字节。
Supports both text (UTF-8) and binary message payloads.
同时支持文本（UTF-8）和二进制消息载荷。
3. URI Schemes and Ports
3. URI 方案与端口
ws:// — WebSocket over plain TCP, default port 80. wss:// — WebSocket over TLS, default port 443.
ws://：基于明文 TCP 的 WebSocket，默认端口 80。 wss://：基于 TLS 的 WebSocket，默认端口 443。
4. Opening Handshake
4. 打开握手

握手由客户端通过带有 Upgrade: websocket 首部的 HTTP GET 请求发起。若服务器接受升级，则以 HTTP 101 Switching Protocols 响应。

客户端请求示例： GET /chat HTTP/1.1 Host: server.example.com Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== Sec-WebSocket-Version: 13
Example server response: HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
服务器响应示例： HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Sec-WebSocket-Accept 的值由客户端的 Sec-WebSocket-Key 与 GUID "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" 拼接后进行 SHA-1 哈希，再进行 Base64 编码得到。
5. Data Framing
5. 数据帧格式
After the handshake, data is transmitted as frames. Each frame has a header that includes an opcode, payload length, and (for client-to-server frames) a masking key. Opcodes include: 0x1 text, 0x2 binary, 0x8 close, 0x9 ping, 0xA pong.
握手完成后，数据以帧的形式传输。每个帧的首部包含操作码、载荷长度，以及（对客户端到服务器的帧）一个掩码密钥。操作码包括：0x1 文本、0x2 二进制、0x8 关闭、0x9 ping、0xA pong。
All client-to-server frames MUST be masked by the client to prevent proxy cache poisoning. Server-to-client frames MUST NOT be masked.
所有客户端到服务器的帧必须由客户端进行掩码处理，以防止代理缓存污染。服务器到客户端的帧不得进行掩码。
6. Closing and Control Frames
6. 关闭与控制帧
Either endpoint may initiate a closing handshake by sending a Close frame (opcode 0x8). The other endpoint responds with its own Close frame, and the underlying TCP connection is then closed.
任一端点均可通过发送关闭帧（操作码 0x8）发起关闭握手。另一端点也以关闭帧响应，随后关闭底层 TCP 连接。
Ping (0x9) and Pong (0xA) frames are used to verify that the connection is alive and to measure latency.
Ping（0x9）和 Pong（0xA）帧用于验证连接仍然存活并测量延迟。

7. 典型应用场景
Real-time chat, collaborative editing, live sports / financial tickers, online multiplayer games, IoT device telemetry, push notifications, live dashboards.
实时聊天、协作编辑、实时体育/金融行情、在线多人游戏、物联网设备遥测、消息推送、实时仪表盘。

RESTful 规范

REST — Representational State Transfer

基于 Roy Fielding 博士论文。REST 是一组架构约束，指导分布式超媒体系统（尤其是 Web API）的设计。

English (Original)

中文对照

1. Overview
1. 概述
REST (Representational State Transfer) is an architectural style for distributed hypermedia systems, introduced and defined by Roy Fielding in his 2000 doctoral dissertation. REST defines a set of constraints that, when applied, induce desirable properties such as performance, scalability, simplicity, modifiability, visibility, portability, and reliability.
REST（表现层状态转移）是一种面向分布式超媒体系统的架构风格，由 Roy Fielding 于 2000 年在其博士论文中提出并定义。REST 定义了一组约束，当这些约束被应用时，将促使系统具备性能、可伸缩性、简洁性、可修改性、可见性、可移植性与可靠性等良好特性。
2. Six Architectural Constraints
2. 六大架构约束
1) Client-Server: Separation of concerns between user interface and data storage, improving portability and scalability.
1) 客户端-服务器：将用户界面与数据存储的关注点分离，提升可移植性和可伸缩性。
2) Stateless: Each request from client to server must contain all the information necessary to understand the request; the server cannot rely on any stored context on the server.
2) 无状态：客户端发往服务器的每个请求必须包含理解该请求所需的全部信息；服务器不能依赖任何存储于服务器端的上下文。
3) Cacheable: Responses must implicitly or explicitly define themselves as cacheable or non-cacheable to prevent clients from reusing stale or inappropriate data.
3) 可缓存：响应必须隐式或显式地声明自身是否可缓存，以防止客户端重用陈旧或不适用的数据。
4) Uniform Interface: A uniform interface between components simplifies and decouples the architecture, and includes: resource identification in requests, manipulation of resources through representations, self-descriptive messages, and HATEOAS (Hypermedia as the Engine of Application State).
4) 统一接口：组件之间采用统一接口，以简化并解耦架构，包括：请求中对资源的标识、通过表示形式操作资源、自描述的消息，以及 HATEOAS（超媒体作为应用状态引擎）。
5) Layered System: A client cannot ordinarily tell whether it is connected directly to the end server, or to an intermediary along the way, enabling intermediaries such as proxies and gateways.
5) 分层系统：客户端通常无法区分是直接连接到终端服务器，还是连接到中间的某个层级，从而使代理、网关等中间层得以实现。
6) Code on Demand (optional): Servers can temporarily extend client functionality by transferring executable code. This is the only optional constraint.
6) 按需代码（可选）：服务器可通过传输可执行代码临时扩展客户端功能。这是唯一一个可选的约束。
3. Resources and URIs
3. 资源与 URI
The key abstraction of information in REST is a resource. Any information that can be named can be a resource: a document, an image, a temporal service, a collection of other resources, a non-virtual object (e.g., a person), and so on.
REST 中信息的关键抽象是资源。任何可命名的信息都可以是资源：文档、图像、临时服务、其他资源的集合、非虚拟对象（如某个人）等等。
Each resource is identified by a URI. Good RESTful URIs use nouns (not verbs), are hierarchical, and use plural names for collections: /users, /users/42, /users/42/orders.
每个资源由 URI 标识。良好的 RESTful URI 使用名词（而非动词），具有层级结构，并对集合使用复数名词：/users、/users/42、/users/42/orders。
4. HTTP Methods Mapping to CRUD
4. HTTP 方法与 CRUD 的映射
GET /users — Retrieve a collection of users (Read). GET /users/{id} — Retrieve a specific user (Read). POST /users — Create a new user (Create). PUT /users/{id} — Fully replace a user (Update). PATCH /users/{id} — Partially update a user (Update). DELETE /users/{id} — Delete a user (Delete).
GET /users —— 获取用户集合（读取）。 GET /users/{id} —— 获取指定用户（读取）。 POST /users —— 创建新用户（创建）。 PUT /users/{id} —— 完整替换指定用户（更新）。 PATCH /users/{id} —— 部分更新指定用户（更新）。 DELETE /users/{id} —— 删除指定用户（删除）。
5. Status Code Conventions
5. 状态码约定
200 OK — successful GET/PUT/PATCH. 201 Created — successful POST that creates a resource, with Location header pointing to the new resource. 204 No Content — successful request with no body (typical DELETE). 400 Bad Request — client-side malformed request. 401 Unauthorized — missing or invalid authentication. 403 Forbidden — authenticated but not allowed. 404 Not Found — resource does not exist. 409 Conflict — resource state conflict (e.g., duplicate key). 422 Unprocessable Entity — semantically invalid payload. 500 Internal Server Error — unexpected server failure.
200 OK —— GET/PUT/PATCH 成功。 201 Created —— POST 创建资源成功，并在 Location 首部中指向新资源。 204 No Content —— 请求成功但无响应体（常用于 DELETE）。 400 Bad Request —— 客户端请求格式错误。 401 Unauthorized —— 缺少或无效的身份认证。 403 Forbidden —— 已认证但无权限。 404 Not Found —— 资源不存在。 409 Conflict —— 资源状态冲突（如唯一键重复）。 422 Unprocessable Entity —— 语义上无效的载荷。 500 Internal Server Error —— 服务器意外故障。
6. Representations
6. 表示形式
REST components perform actions on a resource by using a representation to capture the current or intended state of that resource and transferring that representation between components. JSON is the most common representation format for RESTful APIs today; XML is also used.
REST 组件通过在组件之间传递"表示形式"（用以捕获资源当前或期望的状态）对资源执行操作。如今 JSON 是 RESTful API 最常用的表示格式；XML 也在使用。
Clients and servers use the Accept and Content-Type headers to negotiate representations.
客户端与服务器通过 Accept 和 Content-Type 首部协商表示形式。
7. Design Best Practices
7. 设计最佳实践
Use nouns for resources; use HTTP methods for actions; keep URIs consistent and hierarchical; version the API (e.g., /v1/users or via Accept header); return meaningful HTTP status codes; provide paging, filtering, and sorting via query parameters; use HATEOAS links where appropriate; prefer HTTPS.
对资源使用名词；对动作使用 HTTP 方法；保持 URI 一致且具有层级结构；对 API 进行版本管理（如 /v1/users 或通过 Accept 首部）；返回有语义的 HTTP 状态码；通过查询参数提供分页、过滤和排序；在合适处使用 HATEOAS 链接；优先使用 HTTPS。
